# Spec: Modes (v1)
- Three loops, one flow: `-bish` (requirements -> specs), `-bash` (specs -> plan), `-bosh` (plan -> actual files and configuration in the project root).
- Before either interview or reverse execution, `-bish` automatically asks for the adapter/model and writes config only if `.bish-bash-bosh/config.yml` is missing (`specs/loop.md`). Existing config is validated and reused, never reset. The first-interview template seeding below happens after this setup in the same invocation; setup itself makes no agent call; the README.md prerequisite below is checked first.
- `-bish --reverse`: existing code to a `.bish-bash-bosh/specification.md` describing what it does today.
- `-bish` has a tuned prompt pair in `src/bish/prompts/` (an intro prefaced once, on a brand-new session only, and a loop prompt prefaced every round). `-bash` has an intro and a single planning prompt in `src/bash/prompts/`, sent together in one fresh call. `-bosh` is stateless instead (no intro, no session): a test-writing prompt (`src/bosh/prompts/bosh-test-writer.js`), an implement prompt (`src/bosh/prompts/bosh-builder.js`) and a QA prompt (`src/bosh/prompts/bosh-inspector.js`), each self-contained and loaded fresh on every call.
- The specification captures every requirement of the objective, non-functional ones included (any testing approaches the owner wants are part of it). The harness's own testing is not specified by these artifacts: `-bosh` applies it independently of, and in addition to, any test frameworks or suites the objective specifies. The harness refuses `-bash`/`-bosh` to start without a `specification.md`/`plan.md` respectively.
- All three commands refuse to run (exit 2) unless the project is a git repository. The harness, never the agents, commits (never pushes) via `src/shared/git-commit.js`, staging everything under the project except the harness's own `.bish-bash-bosh/` folder, which is git-ignored entirely (the harness adds it to `.gitignore` and stops tracking anything of it already committed) because it is the means to the end, not part of the solution; so the commits below only exist when the project itself changed: `-bish` after the bootstrap and after each completed interview round (`bish: <question>` with the answer in the body), `-bash` once after the plan is written (`bash: write plan (N tasks, M to build)`), `-bosh` after each completed item (`bosh: <task name>` with its detail, `S:` ids and spec status). Nothing is committed for a paused round or an item that failed.
- `-bish` (always operates on the current directory, `src/bish/bish-analyst-loop.js`) takes no objective flag. `-bish` (not `--reverse`) refuses to start (exit 2) unless `README.md` exists in the project root, checked before any setup prompt. The very first `-bish` run in a project with no `.bish-bash-bosh/interview.md` writes it from `src/bish/templates/bish-interview.md`, writes `.bish-bash-bosh/specification.md` from `src/bish/templates/bish-specification.md`, creates an empty `.bish-bash-bosh/bish-log.md`, then (under the run lock, no run folder) makes one fresh-session agent call with `src/bish/prompts/bish-analyst-init.js` (`src/bish/bish-analyst-init.js`) to turn `README.md` into a baseline specification and the first interview questions, and exits; it does not persist that call's session, so the Interview Loop's first round still gets `bish-analyst-intro.md`. If the agent leaves `specification.md` unchanged or writes no unprocessed question, the seeded `interview.md` and `specification.md` are removed (`bish-log.md` is kept so the failed call can be read), the run fails (exit 2) with the agent's exit status and last output and the next run repeats this step. A restart that somehow lost only `specification.md` rewrites it from the template before continuing. Once those files exist, `-bish` runs the Interview Loop. `interview.md` holds one numbered line per question, `N. [ ] Q: <question> A: <answer>`, with a single checkbox ticked only once that round has been fully handed to and processed by the agent — not as soon as the owner answers. Each round: find the first line not yet checked, show its question in colour, read one line from stdin (on a real terminal, any existing answer is shown in grey ahead of the cursor, not actually part of the editable line — Enter alone accepts it verbatim, recoloring it to the `A:` label's own color as it's accepted, any other keypress clears the whole suggestion at once and the owner's own typing then inherits that same color — see `createAsker`; piped input instead accepts an empty line as that default), write the answer back into that line (checkbox still unticked), show "Analyst thinking..." then call the agent once with a prompt prefaced by `src/bish/prompts/bish-analyst-loop.js`'s instructions and this round's `## Question`/`## Answer` — the very first round of a brand-new session (no session persisted yet) also prefaces `src/bish/prompts/bish-analyst-intro.js` above all of that, once only, never again for a later round or a restart that resumes the same session — (the agent's job: update `.bish-bash-bosh/specification.md`, add further questions with sensible defaults if it judges the spec still incomplete, then stop — by convention, not enforcement, it is expected to touch only `specification.md` and `interview.md`), streaming the agent's own live reasoning text on the line after "Analyst thinking..." in the same grey as it arrives (the adapter contract's opt-in `onReasoning` callback — see `specs/adapters.md`; adapters with no such concept simply never call it, so nothing extra appears), tick the line's checkbox (re-reading the file first and matching by id, since the agent's own call may have appended new lines), and repeat. Every round also appends to `.bish-bash-bosh/bish-log.md`: one `[<ISO timestamp>] bish/analyst prompt: <full prompt sent>` line for the prompt (`bish/analyst` for the first-run call), and, only when the agent streamed any reasoning text, one `[<ISO timestamp>] bish/analyst response: <full accumulated reasoning text>` line for it — plain text only, never the raw JSON behind either, and never the on-screen Q/A/"Analyst thinking..." lines (see `src/bish/bish-log.js`). One native agent session is used across every round of a `-bish` invocation and persists across separate invocations too (the `bishSession` field in `.bish-bash-bosh/config.yml`, written back after every round and named distinctly from other loops since only the Interview Loop uses it — see `specs/adapters.md`'s opt-in `session` field on the adapter request/response contract), so the agent keeps the whole conversation's context rather than starting fresh each round. EOF pauses (status `paused`, remaining count shown) so a rerun resumes where it left off; once no unanswered block is left, it reports `ok`. Exit 0 only when ok.
- `-bash` (always operates on the current directory, `src/bash/bash-planner.js`) takes no objective flag. It refuses to run (exit 2) until `.bish-bash-bosh/specification.md` exists (run `-bish` first). The very first `-bash` run after that writes `.bish-bash-bosh/plan.md` from `src/bash/templates/bash-plan.md` and creates an empty `.bish-bash-bosh/bash-log.md`, then falls straight through into the Plan Pass. The Plan Pass is a single fresh-context agent call (no session) whose prompt is `src/bash/prompts/bash-planner.js`: the agent reads the whole `specification.md` and the project's existing code, does a gap analysis, and writes `plan.md` as a prioritised checklist of concrete construction tasks, most important first, one per numbered line `<n>. [ ] T: <name> - <detail> S: <specification ids>`; ticked items are kept and unticked ones may be rewritten, since the plan is disposable and `-bash` can be re-run to re-plan against the code as it stands. The harness only checks that `plan.md` then has at least one such line (otherwise exit 2 with the agent's last output) and prints `Plan ready: N items ..., M left to build`. The call is logged to `.bish-bash-bosh/bash-log.md` as `[<ISO timestamp>] bash/planner prompt: ...` and, when the agent streamed reasoning, `bash/planner response: ...` (see `src/bish/bish-log.js`). Exit 0 only when ok.
- `-bosh` (always operates on the current directory, `src/bosh/bosh-build-loop.js`) takes no objective flag. It refuses to run (exit 2) until `.bish-bash-bosh/plan.md` exists (run `-bash` first). The first `-bosh` run creates an empty `.bish-bash-bosh/bosh-log.md`, seeds `.bish-bash-bosh/test-harness.js` from `src/bosh/templates/bosh-test-harness.js` (a pure-Node, `node:test`/`node:assert`-based black-box verification harness: `runCommand` and `httpRequest` helpers plus a re-exported `assert`, language-agnostic since it only exercises the project's external behaviour, never its internals) and creates `.bish-bash-bosh/tests/`, then runs the Build Loop. `plan.md`'s build items are numbered lines, `<n>. [ ] T: <name> - <detail> S: <specification ids>` (`S` optional), in priority order: find the first unchecked line and show its name in colour; ticking flips only the checkbox. Unlike `-bish`/`-bash`, `-bosh` never opts into session tracking — every call below is a fresh agent context with no memory of any earlier call, relying instead on `plan.md`'s ticked items and the project's own files to know what already exists. For that one item, each step a fresh agent call retried up to 5 attempts with the failure under `## Previous Failure`: (1) show "Writing tests...", the agent writes only the item's harness verification tests under `.bish-bash-bosh/tests/` (`bosh-test-writer.md`); -bosh's code (`src/bosh/bosh-test-runner.js`) requires new or changed test files and that they run RED (tests that still pass on the second attempt are accepted, since an interrupted earlier run may already have implemented the item); (2) show "Implementing...", the agent implements the item (`bosh-builder.md`) and -bosh's code requires the full suite GREEN; (3) show "Verifying...", the agent independently checks the work against `interview.md`/`specification.md`/`plan.md` and the source, read-only and on the user's behalf (`bosh-inspector.md`): it ends its reply with `APPROVED` (plus `VERIFIED: S1, S2`) or `FEEDBACK: <what must change>`, and feedback goes to the Builder (at most 3 rounds). Only once all three have passed does it re-read `plan.md` and match the recorded line by its index before ticking it (tolerant of concurrent edits: a line that no longer matches is left alone rather than erroring), and repeat until none remain (status `ok`; no pause state, every unprocessed item is handed to the agent in one run, unless a step giving up stops it first). Spec status comes from the Inspector: on approval, `-bosh` ticks the `specification.md` items in its `VERIFIED:` line that belong to the plan item (`src/bosh/bosh-spec-status.js`), then prints `Specification: N verified, N not yet verified`. Every agent call also appends to `.bish-bash-bosh/bosh-log.md`, the same shape as `bish-log.md`/`bash-log.md`, labelled `bosh/tester`, `bosh/builder` or `bosh/verifier` (`prompt`/`response`), with the harness's own gate failures as `bosh/harness`. Exit 0 only when ok, 1 when a gate failure stopped the run, 2 when plan.md is missing or another error occurs.
- `-bish --reverse` (always operates on the current directory) runs the configured `adapter`/`model` with `src/bish/prompts/bish-reverse-engineer.js` + the specification template. It may only write `.bish-bash-bosh/specification.md`; it is accepted only if that file holds at least one well-formed item. Otherwise the work is discarded (status `failed`). Records go to `.bish-bash-bosh/runs/<id>/reverse/`. Exit 0 only when ok.
